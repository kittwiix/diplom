# Дипломная работа: автоматическая ректификация полок (гомография) → ONNX → Java/Android

Тема (рабочая формулировка): **система автоматического выпрямления фотографий стеллажа по гомографии,
обеспечивающая корректное чтение ценников внешней VLM-моделью; прототип на Python, целевая реализация — Java/Android,
нейросетевые модели экспортируются в ONNX с документированным контрактом тензоров.**

---

## 0. Цель, критерии успеха, ограничения

0.1. Вход: JPEG-фото полки, снятое под углом (наклон, поворот, перспектива).
0.2. Выход: изображение, в котором плоскость фасада стеллажа (полка + ценникодержатели) отображается
     фронтально: линии ценникодержателей горизонтальны, вертикали вертикальны, масштаб по полке равномерен.
0.3. Прикладной критерий: цена, прочитанная внешней VLM по warped-изображению, совпадает с эталоном;
     доля корректно распознанных ценников растёт относительно исходного фото.
0.4. Ограничения:
     - математика ректификации, ресемплинг, решатели — **собственная реализация, без OpenCV/BoofCV/ImageMagick**;
     - единственная разрешённая «внешняя» зависимость в рантайме — **ONNX Runtime** (иначе ONNX не имеет смысла);
     - обучение модели — офлайн (PyTorch), в поставку не входит;
     - целевая платформа — Android; десктопный Java-CLI — для отладки и сравнения с Python-эталоном.
0.5. Артефакты защиты: репозиторий (Python + Java + Android), ONNX-модель + спецификация тензоров,
     APK/демо-видео, текст ВКР, слайды, протокол экспериментов.

## 1. M0. Анализ эталонных пар (ВЫПОЛНЕНО)

Метод: Harris-углы → нормализованные patch-дескрипторы (2 масштаба) → ratio-test + mutual NN →
RANSAC DLT (нормализация Хартли) → Levenberg–Marquardt. Только numpy + PIL.

| Пара | Совпадений | Инлайеров | Медианная ошибка репроекции |
|---|---|---|---|
| `photo → photo_warped` | 874 | 547 | **0.74 px** (p90 = 1.41) |
| `photo_2 → photo_2_warped` | 598 | 380 | **0.92 px** (p90 = 1.68) |

Выводы (важно для дизайна):

1.1. Оба «warped» — **строго гомография** исходника (ошибка < 1 px при ширине 1100–1500 px).
1.2. Перспективная составляющая исчезающе мала: `h31 ≈ 2.2e‑4` и `−1.3e‑4`, т.е. сдвиг на уровне < 0.5 px.
     Аффинная часть = поворот ~1° + сдвиг/анизотропный масштаб. Фактически эталоны — это «выровнять полку по горизонтали + кроп».
1.3. Точки схода (ТС) линий полок лежат далеко вне кадра: x ≈ −4572 px и +7787 px.
     **Следствие: регрессировать сами ТС нельзя** (численно неустойчиво, огромный разброс) — модель должна предсказывать
     *линии*, а ТС считать геометрическим решателем.
1.4. Выходные кадры — подквады исходника: `photo_2_warped` = вся ширина, y ∈ [540, 2049]; `photo_warped` ≈ весь кадр.
     **Следствие: гомография определена с точностью до подобия (кроп/масштаб/сдвиг)**, метрику нужно сделать
     инвариантной к этому калибровочному преобразованию (см. 8.2).
1.5. Найденные H сохранены как golden-фикстуры для тестов собственного решателя (Приложение A).

## 2. Архитектура решения (эскиз)

```
фото (JPEG + EXIF) ──► препроцесс (ориентация, даунскейл, letterbox)
                              │
                              ▼
                    ONNX-модель (детектор линий полок / квад)
                              │  K линий (норм. координаты) + confidence
                              ▼
      геометрический решатель (собственный код): ТС линий → линия бесконечности
      + направление гравитации → R → H = K·R·K⁻¹ (+ выбор выходного кадра)
                              │
                              ▼
                 ресемплинг (обратное отображение, bicubic/bilinear + антиалиасинг)
                              │
                              ▼
      выход 1: полный rectified-кадр       выход 2: полосы ценникодержателей (кропы для VLM)
```

Два уровня:
- **A (база, для каркаса):** 4 точки → DLT → H. Работает всегда, в т.ч. вручную.
- **B (целевой):** K линий полок + гравитация → метрически корректная R-гомография. Устойчиво при ТС вне кадра.

## 3. Блоки работ

### Блок 1. Теория и математическая база (документ `docs/THEORY.md`)
1.1. Проективная плоскость P²: однородные координаты, прямая = ко-вектор, точка = кросс-произведение прямых.
1.2. Гомография 3×3, 8 степеней свободы, индуцированная плоскостью: `x' = H x`, `H = K (R + t nᵀ/d) K⁻¹`.
1.3. Гомография, индуцированная **чистым вращением**: `H = K R K⁻¹` (не зависит от глубины) — основа варианта B.
1.4. DLT: 2 уравнения на соответствие, матрица 8×9, `h = argmin ||A h||` через SVD; нормализация Хартли;
     вырожденные конфигурации (3 коллинеарные точки, «тонкий» квад).
1.5. Восстановление ТС из набора линий: `v = null([l₁ᵀ; …; l_Kᵀ])`; IRLS/RANSAC для выбросов;
     случай ТС на бесконечности (`l∞`).
1.6. Аффинная и метрическая ректификация (конические точки, `ω = K⁻ᵀK⁻¹`), связь с ТС и перпендикулярностью.
1.7. Внутренние параметры: `f` из EXIF (35 мм эквивалент → px), допущения о нулевом skew и главной точке в центре.
1.8. Гравитация как источник вертикального направления (Android `TYPE_ROTATION_VECTOR`/`TYPE_GRAVITY`),
     погрешность акселерометра и её влияние на H.
1.9. Ресемплинг: прямое/обратное отображение, билинейная/бикубическая (Catmull–Rom) интерполяция,
     префильтрация при уменьшении (box-фильтр/суперсэмплинг), LOD/mipmap в GLES, краевые условия.
1.10. Численная устойчивость: обусловленность, масштабирование координат, Jacobi-SVD, LM-уточнение по ошибке репроекции.
1.11. Оценка неопределённости H (через `JᵀJ`) → «уверенность» системы и отказ от плохих кадров.
1.12. Обзор аналогов: OpenCV `findHomography`/`warpPerspective`, DocTr/DewarpNet/UVDoc, LSD/Hough,
     single-view metrology (Criminisi), коммерческие SDK — и обоснование собственной реализации.

### Блок 2. Python-прототип без CV-библиотек (это и есть «каркас»)
2.1. Структура пакета `python/rectif/` (geometry, warp, frame, detectors, pipeline, metrics, io).
2.2. `geometry.py`: нормализация, DLT (SVD/Якоби), `homography_from_points`, `vp_from_lines`, `homography_from_rotation`,
     `refine_lm`, `decompose` (поворот/масштаб/сдвиг/перспектива), отчёт о вырожденности.
2.3. `warp.py`: собственная `warp_perspective` (обратное отображение, bilinear + bicubic, суперсэмплинг 2×2/4×4,
     предвычисление карты сэмплов, тайлинг, float32/uint8).
2.4. `frame.py`: выбор выходного кадра — авто-кроп по полосе стеллажа, сохранение масштаба, оценка «px на мм»
     (по шагу полок/высоте ценника), ограничение размера выхода.
2.5. `detectors.py`: (а) ручные/JSON-точки, (б) классический детектор (Hough на градиентах + RANSAC) — baseline без НС,
     (в) ONNX-обёртка.
2.6. `pipeline.py`: единый `rectify(image, config) -> Result{image, H, lines, conf, debug}`, детерминизм, логирование.
2.7. CLI: `rectify.py --in a.jpg --points points.json --out b.jpg`, `--debug` (оверлей линий/квада/сетки).
2.8. Тесты (`pytest`):
     - юнит: DLT на синтетике (случайные H, шум, выбросы), восстановление H по 4 точкам с точностью 1e-9;
     - golden: воспроизведение H из M0 (допуск 1 px по сетке точек);
     - инвариантность: `H` и `sH` дают одинаковый результат;
     - качество ресемплинга: PSNR/SSIM к эталону, отсутствие «лесенок» на мире-сетке.
2.9. Сравнение с OpenCV — **только в dev-скрипте** (вне поставки), как контроль корректности.
2.10. Бенчмарк: время на кадр 12 Мп с разбивкой по стадиям.

## 4. Математика варианта B (кратко)

1. Модель даёт набор линий ценникодержателей `l_i = (a_i, b_i, c_i)` (нормированные координаты ×W, ×H).
2. Устойчивая оценка ТС горизонтального направления: `v_h = argmin Σ w_i (l_iᵀ v)²`, `||v||=1`
   (SVD 3×3; веса `w_i` из confidence/IRLS). Случай `v_h,w ≈ 0` → направление на бесконечности (чистый roll).
3. Направление в 3D: `d_h = normalize(K⁻¹ v_h)`; вертикаль из гравитации `d_v = g` (Android) или
   `d_v = normalize(K⁻¹ v_v)`, где `v_v` — из вертикальных кромок (fallback: `d_v = (0,1,0)` в координатах камеры).
4. Ортонормированный базис: `d_h ← normalize(d_h − (d_h·d_v) d_v)`, `n = d_h × d_v`; `R = [d_h; d_v; n]ᵀ`.
5. `H = K R K⁻¹` → плоскость фасада становится фронтальной, прямые полок — горизонтальными.
6. Доворот на остаточный угол (по медианному наклону линий после варпа) + выбор масштаба/кропа (`frame.py`).
7. Точность `f` уточняется по EXIF; при отсутствии — по допущению (ТС горизонтали на бесконечности) или
   1-мерной оптимизацией `f` по остаточной невязке прямых после варпа.

Свойства: ТС может быть сколь угодно далеко (предельный переход корректен), нет вырожденности «4 точки вне кадра»,
ошибка в `f` даёт плавную деградацию, а не отказ.

## 5. Контракт ONNX (черновик, финализируется в `docs/SPEC-model-io.md`)

Модель `shelf_lines_v1.onnx` (вариант 4.1a):

| | имя | тип | форма | семантика |
|---|---|---|---|---|
| вход | `images` | float32 | `[1,3,512,512]` | RGB, `x/255`, нормализация ImageNet; letterbox (пропорции, паддинг 114/255) |
| выход | `line_y` | float32 | `[1,K,64,1]` | `y_norm ∈ [0,1]` для полки `k` в колонке `x_j = (j+0.5)/64`; `-1` = полка не видна |
| выход | `line_conf` | float32 | `[1,K]` | уверенность в линии (сигмоида) |

`K = 6` (макс. число полок), упорядочение сверху вниз по `y` при `x = 0.5`.
Постобработка: порог по `conf`, RANSAC-подгонка прямой по валидным колонкам, перевод в пиксели через
`scale`/`pad` препроцесса (параметры letterbox в тензор не входят — они известны из метаданных и одинаковы во всех реализациях).

MVP-модель `shelf_quad_v1.onnx`: вход тот же, выход `quad [1,4,2]` (TL, TR, BR, BL) + `conf [1]`.

## 7. Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Нет PyTorch/GPU в окружении (сейчас Python 3.14, torch отсутствует) | блокирует Блок 4 | отдельный venv Python 3.11/3.12 + torch; синтетика компактна → обучение на CPU реально |
| Нет Android SDK на машине | блокирует Блок 7 | установка SDK/Studio или сборка на другой машине; Java-модуль тестируется независимо |
| Мало реальных фото | падение качества | синтетическое предобучение + Hough-fallback + ручные точки |
| ТС далеко/внутри кадра | численные сбои | решатель по линиям в однородных координатах + проверки правдоподобия |
| Разная глубина полок (параллакс) | остаточные искажения | эксперимент «H на полосу», кропы для VLM |
| Нет доступа к внешней VLM | нет главной метрики | заменить на локальную VLM/OCR (Tesseract как прокси), зафиксировать в тексте |
| «Без сторонних библиотек» трактуется строго | конфликт с ONNX Runtime | согласовать формулировку: ORT = среда исполнения модели, не библиотека алгоритма |

## 9. Стадия 1 — реализовано (M1, прототип `python/rectif`)

### 9.1. Что сделано
- `imageops.py` — серые тона, box-блюр, градиенты, билинейный ресайз (numpy).
- `lines.py` — детектор кромок полок и вертикалей: отклик на горизонтальные кромки -> профили в полосах ->
  пики (субпиксельно) -> RANSAC-связывание в прямые с отбраковкой по покрытию полос.
- `geometry.py` — DLT с нормализацией Хартли (SVD), LM-уточнение, ТС из семейства прямых,
  аффинная + метрическая ректификация (`rectifying_homography`), `recenter` (сдвиг выхода), `fit_frame`.
- `warp.py` — собственный `warp_perspective` (обратное отображение, билинейно, суперсэмплинг 1–3x).
- `pipeline.py` — `analyze` / `rectify(mode='vp'|'directions'|'roll')` / `crop_cells`, самоконтроль качества.
- `debug.py`, `cli.py`, `tools/demo_stage1.py`, `tools/make_report.py`, `tests/` (5 тестов, все зелёные).
- обрезка чёрных углов (`largest_inscribed_rect`), метрика качества (`quality.score`), JSON-метаданные,
  режимы `vp/directions/roll`, `--cells-dir` для кропов полок.
- скорость: тайловый варп + префильтр вместо суперсэмплинга + векторизованный RANSAC -> 1.0–1.3 с/кадр.

### 9.2. Ключевые измерения на реальных фото

| Фото | Полок | Разброс углов ДО | RMS после | Разброс после |
|---|---|---|---|---|
| photo | 10 | 19.8° | **0.27°** | 0.79° |
| photo_2 | 8 | 20.3° | **0.07°** | 0.23° |
| photo_warped | 9 | 2.7° | 0.23° | 0.64° |
| photo_2_warped | 6 | 5.8° | 0.03° | 0.08° |

### 9.3. Что выяснилось (важно для текста ВКР)
1. **Полки образуют веер**: углы кромок одного стеллажа расходятся до 20° (то есть одного поворота мало,
   нужна настоящая гомография). Разброс объясняется перспективой и подтверждается тем, что
   после приведения ТС к бесконечности он падает до < 1°.
2. Эталонные `*_warped` — результат *приблизительного* выпрямления: в них остаётся веер 2.7° и 5.8°.
   Поэтому метрика «совпасть с эталоном попиксельно» некорректна; правильная — **остаточный угол полок**.
3. Метрика `rails_angle_rms_deg` / `rails_angle_spread_deg` считается без разметки (self-supervised) —
   годится и как критерий качества, и как функция потерь при обучении.
4. Проективную H **нельзя** «вращать вокруг точки» сопряжением с трансляцией: это меняет перспективу.
   Правильно — сдвигать выход (`recenter`). Ошибка стоила 16° остаточного угла, теперь есть тест.
5. В `np.linalg.svd` для матрицы 8x9 нужен `full_matrices=True`, иначе вектор нуль-пространства
   (последняя строка Vt) теряется.

### 9.4. Что осталось в M1/M2
- Hough/классический baseline для сравнения (сейчас есть только RANSAC-детектор).
- Скорость: 1.0–1.3 с/кадр -> цель < 0.3 с (cache карт сэмплов, SIMD/Java, меньше итераций).
- Вертикали: детектор слабый (товары короткие) -> пока используется допущение «вертикали вертикальны»;
  нужен отдельный источник (EXIF + гравитация на Android).
- Оценка по VLM (Блок 8.3) и CLI-обёртка с JSON.
